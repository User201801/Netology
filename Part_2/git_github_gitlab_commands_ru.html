1. Git — команды по алфавиту

Команды отсортированы по названию подкоманды. Добавлены получение удалённых изменений, синхронизация, сравнение, восстановление, временное сохранение и современная работа с ветками.

01

git --version

Показывает установленную версию Git.

Параметры команды
git
Запуск программы Git.
--version / -v
Вывести версию и завершить работу.
Примеры с описанием
git --version

Показать версию.

git -v

Короткая форма.

02

git add -A

Подготавливает все новые, изменённые и удалённые файлы во всём рабочем дереве.

Важно. Перед массовым добавлением проверьте git status и git diff --cached.
Параметры команды
add
Обновляет индекс — область подготовки следующего коммита.
-A / --all
Учитывает новые файлы, изменения и удаления.
Примеры с описанием
git add -A

Подготовить все изменения.

git add -A src/

Подготовить изменения только внутри src/.

git diff --cached

Проверить содержимое индекса.

03

git add имя_файла

Помещает текущую версию выбранного файла в индекс.

Примечание. Если после git add файл изменился снова, выполните git add ещё раз.
Параметры и обозначения путей
add
Обновляет индекс содержимым выбранных путей.
имя_файла
Путь к одному файлу, например README.md или src/app.js.
каталог/
Путь к каталогу. Git обработает подходящие файлы внутри него и во вложенных каталогах.
.
Специальный путь: текущий каталог и всё его содержимое. Это не параметр с дефисом, а pathspec — обозначение выбранного пути.
--
Обозначает конец параметров. Всё после -- Git воспринимает как пути, даже если имя начинается с дефиса.
-p / --patch
Интерактивно выбрать отдельные фрагменты изменений вместо добавления файла целиком.
Примеры с описанием
git add README.md

Подготовить один файл.

git add src/

Подготовить изменения внутри каталога src и его вложенных каталогов.

git add .

Подготовить изменения в текущем каталоге и ниже. Если команда выполняется из корня репозитория, она охватывает весь рабочий проект.

git add -- "Мои документы/"

Подготовить каталог с пробелами или кириллицей.

git add -- -archive/

Подготовить каталог, имя которого начинается с дефиса.

git add -p README.md

Интерактивно выбрать отдельные фрагменты файла.

04

git branch

Показывает локальные ветки; текущая ветка отмечается звёздочкой.

Параметры команды
branch
Просмотр и управление ветками.
-a / --all
Показать локальные и удалённо-отслеживаемые ветки.
-vv
Показать последние коммиты и upstream-связи.
Примеры с описанием
git branch

Показать локальные ветки.

git branch -a

Показать все известные ветки.

git branch -vv

Показать upstream и состояние отслеживания.

05

git branch -d new-branch

Удаляет локальную ветку, если её изменения уже слиты.

Важно. -D может сделать неслитые коммиты недоступными по имени ветки.
Параметры команды
-d / --delete
Безопасное удаление слитой ветки.
-D
Принудительное удаление.
new-branch
Имя удаляемой ветки.
Примеры с описанием
git switch main
git branch -d new-branch

Переключиться и безопасно удалить ветку.

git branch -D abandoned

Принудительно удалить локальную ветку.

git push origin --delete new-branch

Удалить ветку на сервере.

06

git branch -M main

Переименовывает текущую локальную ветку в main. Обычно используется перед первой публикацией нового репозитория.

Важно. Если ветка уже опубликована под старым именем, переименование локальной ветки не удалит старую удалённую ветку автоматически.
Параметры команды
branch
Управляет локальными ветками.
-M
Принудительно переименовывает ветку, даже если ветка с новым именем уже существует.
main
Новое имя текущей ветки.
Примеры с описанием 
git branch -M main

Переименовать текущую ветку в main.

git branch -m develop

Переименовать текущую ветку в develop без принудительной замены.

07

git branch new-branch

Создаёт ветку на текущем коммите, но не переключается на неё.

Параметры команды
new-branch
Имя новой ветки.
[точка_старта]
Необязательная база ветки.
Примеры с описанием
git branch new-branch

Создать ветку и остаться в текущей.

git branch hotfix main

Создать hotfix от main.

git switch -c new-branch

Создать и сразу переключиться.

08

git checkout --ours Readme.md

Во время конфликта выбирает вариант файла со стороны ours; после этого нужен git add.

Важно. При rebase смысл ours/theirs может казаться обратным; проверяйте итоговый файл.
Параметры команды
--ours
Выбрать сторону ours.
Readme.md
Путь конфликтующего файла.
--theirs
Выбрать противоположную сторону.
Примеры с описанием
git checkout --ours README.md
git add README.md

Выбрать ours и отметить конфликт разрешённым.

git restore --ours README.md
git add README.md

Современная специализированная форма.

git checkout --theirs README.md
git add README.md

Выбрать theirs.

09

git checkout -b имя_ветки

Создаёт новую ветку от текущего коммита и сразу переключается на неё.

Параметры команды
-b
Создать ветку и переключиться.
имя_ветки
Имя новой ветки.
[точка_старта]
Необязательная база ветки.
Примеры с описанием
git checkout -b feature/login

Создать ветку от HEAD.

git checkout -b hotfix main

Создать ветку от main.

git switch -c feature/login

Современный эквивалент.

10

git checkout main

Переключает рабочую директорию и индекс на существующую ветку main.

Примечание. Git может отказаться переключаться, если будут перезаписаны незакоммиченные изменения.
Параметры команды
main
Имя локальной ветки.
Примеры с описанием
git checkout main

Классический вариант.

git switch main

Современный вариант.

git switch -

Вернуться на предыдущую ветку.

11

git checkout хэш

Открывает состояние указанного коммита и переводит HEAD в detached HEAD.

Важно. Коммиты в detached HEAD легко потерять из вида, если не создать ветку.
Параметры команды
хэш
Полный или однозначный сокращённый ID коммита.
--detach
Явно выбрать отсоединённый режим.
Примеры с описанием
git checkout a1b2c3d

Открыть старый коммит.

git switch --detach a1b2c3d

Современный явный вариант.

git switch -c investigation

Сохранить работу в новой ветке.

12

git clone ссылка

Клонирует удалённый репозиторий, создаёт локальный каталог и remote origin.

Примечание. Fork создаётся на сайте GitHub/GitLab; git clone только копирует репозиторий.
Параметры команды
clone
Создание локальной копии.
ссылка
SSH- или HTTPS-URL.
[каталог]
Необязательное имя локального каталога.
--depth N
Ограничить глубину истории.
Примеры с описанием
git clone git@github.com:User201801/Netology.git

Клонировать по SSH.

git clone https://gitlab.com/group/project.git

Клонировать по HTTPS.

git clone URL project-local

Задать имя локального каталога.

13

git commit --amend -m "комментарий"

Заменяет последний коммит новым: меняет сообщение и/или добавляет подготовленные изменения.

Важно. Хэш изменится; не переписывайте общую опубликованную историю без согласования.
Параметры команды
--amend
Пересоздать последний коммит.
-m
Задать новое сообщение.
--no-edit
Сохранить прежнее сообщение.
Примеры с описанием
git commit --amend -m "Исправить заголовок README"

Изменить сообщение.

git add forgotten.txt
git commit --amend --no-edit

Добавить забытый файл.

git show --stat HEAD

Проверить результат.

14

git commit -m "Комментарий"

Создаёт коммит из содержимого индекса и записывает сообщение.

Параметры команды

Создать снимок подготовленных изменений.
-m / --message
Передать сообщение в командной строке.
"Комментарий"
Краткое описание цели изменения.
Примеры с описанием

Создать коммит.

git commit -m "Исправить форму" -m "Проверять пустой email."

Заголовок и отдельный абзац.

git commit

Открыть редактор сообщения.

15

Читать глобальную конфигурацию.

16

git config --global core.autocrlf true

Включает нормализацию окончаний строк; типичная глобальная настройка Windows.

Важно. В командном проекте дополнительно фиксируйте правила в .gitattributes.
Параметры команды
core.autocrlf
Правило преобразования LF/CRLF.
true
LF→CRLF при извлечении, CRLF→LF при добавлении.
input
Только CRLF→LF при добавлении.
Примеры с описанием
git config --global core.autocrlf true

Распространённый вариант Windows.

git config --global core.autocrlf input

Частый вариант Linux/macOS.

git config --global --get core.autocrlf

Проверить значение.

17

git config --global core.quotePath false

Показывает не-ASCII символы в путях читаемо.

Примечание. Вариант core.quotepath обычно тоже работает, но в документации принято core.quotePath.
Параметры команды
core.quotePath
Ключ отображения путей.
false / off
Отключить экранирование символов выше 0x80.
Примеры с описанием
git config --global core.quotePath false

Сделать кириллические пути читаемыми.

git status

Проверить вывод.

git config --global --get core.quotePath

Проверить значение.

Строгий режим.

git config --global --get core.safecrlf

Проверить значение.

22

git diff

Показывает различия между рабочими файлами, индексом и коммитами. Команда ничего не изменяет и подходит для проверки перед добавлением или коммитом.

Параметры команды
без параметров
Показывает незаписанные в индекс изменения: рабочая директория против индекса.
--staged / --cached
Показывает подготовленные изменения: индекс против последнего коммита.
HEAD
Показывает все локальные изменения относительно последнего коммита.
-- имя_файла
Ограничивает сравнение выбранным файлом или каталогом.
Примеры с описанием 
git diff

Проверить изменения, которые ещё не добавлены командой git add.

git diff --staged

Проверить содержимое будущего коммита.

git diff HEAD -- README.md

Показать все изменения файла README.md относительно последнего коммита.

23

git fetch

Загружает новые коммиты, ветки и теги из удалённого репозитория, но не изменяет текущую ветку и рабочие файлы.

Примечание. После git fetch можно безопасно изучить изменения через git status, git log или git diff.
Параметры команды
origin
Имя удалённого репозитория. Обычно основной удалённый репозиторий называется origin.
--all
Получает данные из всех настроенных удалённых репозиториев.
--prune
Удаляет устаревшие ссылки на удалённые ветки, которых больше нет на сервере.
имя_ветки
Получает сведения только о выбранной ветке.
Примеры с описанием 
git fetch origin

Получить свежие сведения из удалённого репозитория origin.

git fetch --all --prune

Обновить ссылки всех удалённых репозиториев и убрать устаревшие ветки.

git fetch origin main

Получить данные удалённой ветки main.

31

git pull

Получает изменения из удалённого репозитория и сразу интегрирует их в текущую локальную ветку. Фактически сначала выполняется получение данных, а затем слияние или перебазирование.

Важно. Перед git pull --rebase желательно иметь чистую рабочую директорию. Незакоммиченные изменения сначала зафиксируйте или временно сохраните.
Параметры команды
без параметров
Использует удалённую ветку, настроенную как upstream для текущей ветки.
--rebase
Переносит локальные коммиты поверх полученных удалённых коммитов.
--ff-only

git reset

Перемещает указатель ветки и при необходимости изменяет индекс или рабочие файлы. Подходит для снятия файлов с подготовки и отмены локальных коммитов.

Важно. git reset --hard безвозвратно удаляет незакоммиченные изменения отслеживаемых файлов.
Параметры команды
HEAD имя_файла
Убирает файл из индекса, сохраняя изменения в рабочей директории.
--soft
Перемещает ветку, но оставляет изменения подготовленными в индексе.
--mixed
Режим по умолчанию: сбрасывает индекс, но сохраняет рабочие файлы.
--hard

Примеры с описанием

Отменить последний локальный коммит и оставить его изменения подготовленными.

Удалить все отслеживаемые локальные изменения.

Установка GitHub CLI (gh)

gh — отдельная программа и не устанавливается вместе с Git. Сначала установите GitHub CLI подходящим для вашей операционной системы способом, затем проверьте версию и выполните авторизацию.

Требуется доустановка. Без установленного приложения команды gh issue, gh pr и gh repo завершатся сообщением о неизвестной команде.

Стандартный менеджер пакетов современных версий Windows. После установки может потребоваться открыть новое окно Windows Terminal.
Homebrew
Менеджер пакетов для macOS; также может использоваться в Linux. Если brew отсутствует, сначала установите Homebrew.
apt
Менеджер пакетов Debian/Ubuntu. Для актуальной версии GitHub рекомендует подключить официальный репозиторий GitHub CLI.
dnf
Менеджер пакетов Fedora/RHEL. Синтаксис добавления репозитория отличается для DNF4 и DNF5.
gh --version
Проверяет, что приложение установлено и доступно через PATH.
gh auth login
После установки авторизует CLI в GitHub.com или GitHub Enterprise.
Команды установки и проверки 
winget install --id GitHub.cli --source winget

WindowsОфициальный рекомендуемый способ установки через WinGet.

macOSУстановка через Homebrew. Эта же команда доступна в Linux с установленным Homebrew.

(type -p wget >/dev/null || (sudo apt update && sudo apt install wget -y)) \
  && sudo mkdir -p -m 755 /etc/apt/keyrings \
  && out=$(mktemp) && wget -nv -O$out https://cli.github.com/packages/githubcli-archive-keyring.gpg \
  && cat $out | sudo tee /etc/apt/keyrings/githubcli-archive-keyring.gpg > /dev/null \
  && sudo chmod go+r /etc/apt/keyrings/githubcli-archive-keyring.gpg \
  && sudo mkdir -p -m 755 /etc/apt/sources.list.d \
  && echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" \
     | sudo tee /etc/apt/sources.list.d/github-cli.list > /dev/null \
  && sudo apt update \
  && sudo apt install gh -y

Debian / UbuntuПодключить официальный репозиторий GitHub CLI и установить пакет gh.

5. Общая схема работы с репозиторием

Три отдельных сценария: первая публикация, обычное обновление и обновление, когда удалённая ветка изменилась во время локальной работы.

01

Первая публикация проекта

Выполняется один раз, когда локальная папка впервые превращается в Git-репозиторий и связывается с удалённым репозиторием.

Примечание. Замените URL_РЕПОЗИТОРИЯ адресом репозитория GitHub или GitLab.
Показать команды первой публикации
  1. 1
    git init

    Создать локальный Git-репозиторий в текущем каталоге.

  2. 2
    git add .

    Добавить текущие файлы и изменения в индекс.

  3. 3
    git commit -m "Первый коммит"

    Создать первый коммит.

  4. 4
    git branch -M main

    Назвать основную ветку main.

  5. 5
    git remote add origin URL_РЕПОЗИТОРИЯ

    Связать локальный репозиторий с удалённым.

  6. 6
    git push -u origin main

    Отправить первый коммит и настроить отслеживание ветки.

git init
git add .
git commit -m "Первый коммит"
git branch -M main
git remote add origin URL_РЕПОЗИТОРИЯ
git push -u origin main

Полная последовательность для первой публикации локального проекта.

02

Последующие обновления

Перед новым коммитом сначала проверьте, не появились ли изменения в удалённом репозитории, и синхронизируйте локальную ветку.

Примечание. Команды git init, git remote add и git push -u повторять не нужно.
Важно. Выполняйте git pull --rebase при чистой рабочей директории. Если локальные файлы уже изменены, сначала зафиксируйте изменения или временно сохраните их с помощью git stash.
Показать команды обычного обновления
  1. 1
    git fetch origin

    Получить сведения о новых удалённых коммитах без изменения локальных файлов.

  2. 2
    git status

    Проверить состояние файлов и увидеть, отстаёт ли локальная ветка от удалённой.

  3. 3
    git pull --rebase

    Загрузить удалённые изменения и аккуратно применить поверх них локальные коммиты.

  4. 4
    git add .

    Подготовить изменённые, новые и удалённые файлы.

  5. 5
    git commit -m "Описание изменений"

    Зафиксировать подготовленные изменения.

  6. 6
    git push

    Отправить новый коммит в удалённый репозиторий.

git fetch origin
git status
git pull --rebase
git add .
git commit -m "Описание изменений"
git push

Полная последовательность проверки, синхронизации и публикации обновления.

03

Удалённая ветка изменилась во время локальной работы

Используйте этот отдельный сценарий, когда в локальных файлах уже есть незакоммиченные правки, а в удалённой ветке за это время появились новые коммиты.

Смысл схемы. Сначала локальные правки временно сохраняются через git stash. Затем удалённые изменения загружаются и объединяются с локальной веткой через git fetch и git merge. После этого свои правки можно вернуть.
Важно. В примере используется ветка main. Если вы работаете в другой ветке, замените main её именем. Конфликт может возникнуть как во время git merge, так и после git stash pop.
Показать команды синхронизации через merge и stash
  1. 1
    git status

    Проверить текущую ветку и список локально изменённых файлов.

  2. 2
    git stash push -u -m "Перед синхронизацией"

    Временно сохранить локальные правки и новые неотслеживаемые файлы.

  3. 3
    git fetch origin

    Получить сведения о новых коммитах удалённого репозитория без изменения файлов.

  4. 4
    git merge origin/main

    Объединить обновлённую удалённую ветку main с текущей локальной веткой.

  5. 5
    git stash pop

    Вернуть свои незакоммиченные правки поверх обновлённой локальной ветки.

  6. 6
    git status

    Проверить, появились ли конфликты после merge или восстановления stash.

  7. 7
    git add .

    После разрешения конфликтов подготовить итоговые изменения к коммиту.

  8. 8
    git commit -m "Объединение изменений"

    Зафиксировать локальные правки и результат объединения.

  9. 9
    git push

    Отправить согласованную историю в удалённый репозиторий.

git status
git stash push -u -m "Перед синхронизацией"
git fetch origin
git merge origin/main
git stash pop
git status
git add .
git commit -m "Объединение изменений"
git push

Отдельная последовательность для случая, когда локальные правки уже есть, а удалённая ветка изменилась во время работы.
